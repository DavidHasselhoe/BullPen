# Server-side rendering and SEO at BullPen (2026-11-26)

Question from David: *What is server-side rendering, do we use it for BullPen, and how important is it for SEO?*

**Short answer.** Yes, BullPen server-renders most of its public pages, and most of them are in good shape. A crawler with no JavaScript gets the full content of the landing page, `/stocks`, every glossary term, the 212 compare pages, the economy pages, the stock subpages, and the politician and fund pages. **But the stock page's own main content is browser-only.** That page is the bulk of the sitemap. The same goes for `/academy`, `/picks/*` and `/asset/*`. Those sections load their data from `/api/...`, and `robots.txt` blocks `/api/` for every crawler. So **even Google, which does run JavaScript, most likely can't see them.** That is the one gap worth fixing.

---

## 1. The terms in plain language

A page reaches a visitor in one of two ways.

- **Client-side rendering (CSR).** The server sends an almost empty page plus JavaScript. The browser runs the JavaScript, asks the server for the data, and only then draws the content. Something that doesn't run JavaScript (most crawlers) sees the empty page.
- **Server-side rendering (SSR).** The server builds the finished HTML, with the text and numbers already in it, and sends that. The browser shows it at once, then runs JavaScript to make buttons work ("hydration"). Any crawler reads the content straight from the HTML.

The page can be built at different times:

- **Static generation.** The HTML is built once, at deploy time, and served from the CDN to everyone. In BullPen, the glossary terms and economy pages list their URLs up front with `generateStaticParams`.
- **ISR (incremental static regeneration).** Static, but rebuilt every N seconds. The economy pages use `revalidate = 900`, so they are rebuilt at most every 15 minutes.
- **Dynamic.** Built fresh on every request. Most BullPen pages work this way. Signed-out stock pages are also cached on Vercel's CDN through a middleware rewrite to `app/cached-stock`.

**React Server Components (Next.js 16 App Router).** Every `page.tsx` and `layout.tsx` is a *Server Component* by default. It runs only on the server and can read the database directly. A file marked `'use client'` is a *Client Component*. **A Client Component is still rendered to HTML on the server first.** The Next 16 docs say so directly: "Client Components and the RSC Payload are used to prerender HTML" (`node_modules/next/dist/docs/01-app/01-getting-started/05-server-and-client-components.md`). So `'use client'` alone does not hide anything from Google. Content goes missing from the first HTML only when:

1. its data is fetched **in the browser** (a TanStack `useQuery` that calls `fetch('/api/...')`, or a `fetch` inside `useEffect`), and the server didn't prefetch it, or
2. the component is loaded with `dynamic(() => import(...), { ssr: false })`, or
3. it renders only after the browser checks something (signed in, mounted).

BullPen does not use Next 16's new `cacheComponents` / `'use cache'` model. It runs on the previous model (`revalidate`, `dynamic`, `generateStaticParams`), which is fine.

## 2. How much SSR matters for SEO today

- **Google renders JavaScript, but later, in a second pass.** Googlebot first fetches the raw HTML. Then it puts the page in a queue for a headless Chromium to run the JavaScript, and only after that does it index what appeared ([Google: JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)). A Vercel and MERJ study of more than 100,000 Googlebot fetches measured that wait: median 10 s, 75th percentile 26 s, 90th percentile about 3 hours ([Vercel](https://vercel.com/blog/how-google-handles-javascript-throughout-the-indexing-process)). So for Google, client-rendered content is *usually* seen in the end, just more slowly and less reliably.
- **Google can't see content that needs a resource blocked by robots.txt.** The renderer obeys robots.txt for every file and data request the page makes. Google's Martin Splitt: it is "potentially problematic if your content only shows up when we can fetch these resources and we don't see the content in the rendered HTML because it's blocked by robots.txt" ([Search Engine Journal](https://searchenginejournal.com/google-says-its-okay-to-block-some-javascript-resources-with-robots-txt/595736); see also [Google: Fix Search-related JavaScript problems](https://developers.google.com/search/docs/guides/fix-search-javascript)). **This is the part that hits BullPen** (section 4).
- **Google's own recommendation is SSR or static rendering.** It now calls "dynamic rendering" (a separate pre-rendered copy served only to bots) a workaround and points to server-side rendering, static rendering or hydration instead ([Google: dynamic rendering as a workaround](https://developers.google.com/search/docs/guides/dynamic-rendering), [Search Engine Land](https://searchengineland.com/google-no-longer-recommends-using-dynamic-rendering-for-google-search-387054)). SSR does not earn a ranking *bonus* in itself. John Mueller has said there is no ranking difference between the two approaches ([SE Roundtable](https://www.seroundtable.com/google-seo-dynamic-rendering-or-server-side-rendering-33947.html)). What SSR buys you is being seen, completely and quickly.
- **Bing renders JavaScript too, but less well at scale.** Its guidance recommends pre-rendered HTML for crawlers on large JavaScript-heavy sites ([Bing webmaster blog](https://blogs.bing.com/webmaster/october-2018/bingbot-Series-JavaScript,-Dynamic-Rendering,-and-Cloaking-Oh-My)).
- **AI crawlers don't run JavaScript at all.** According to the same Vercel and MERJ log study, OpenAI's GPTBot and OAI-SearchBot, Anthropic's ClaudeBot and PerplexityBot fetch the HTML but don't execute it ([Vercel: The rise of the AI crawler](https://vercel.com/blog/the-rise-of-the-ai-crawler), Dec 2024; the vendors don't document their rendering). Anything browser-only is invisible to ChatGPT, Claude and Perplexity answers. For a product that wants to be the answer to "what does Apple's health score look like", that is a growing traffic source.
- **Core Web Vitals are a real but modest ranking input.** Google: "Core Web Vitals are used by our ranking systems". It also says good scores don't guarantee top rankings and that relevance comes first ([Google: Core Web Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals), [page experience](https://developers.google.com/search/docs/appearance/page-experience)). SSR helps LCP because the main content arrives with the HTML instead of after a second round trip. BullPen already did this work in September (stock page snapshot prefetch, fra1 region).

**Verdict on importance.** For Google, SSR is mainly about speed and reliability of indexing. It is critical only where client-side data is blocked or fails, which is exactly BullPen's case. For Bing and AI search, SSR decides whether the content exists at all. Treat "main content is in the first HTML" as a hard rule for every page in the sitemap.

## 4. Why "Google renders JavaScript" doesn't save the browser-only parts

`app/robots.ts` sends `Disallow: /api/` to `User-Agent: *`. That rule is deliberate: it keeps crawlers from spending TwelveData credits on API routes. Every browser-only section above gets its data from `/api/...`:

- stock page: `/api/stock/T`, `/company-profile`, `/health-score`, `/financials`, and so on
- `/academy`: `/api/academy/courses`
- `/picks/*`: the pick detail API
- economy hub: `/api/economy/summary`

When Google's renderer runs the page, those requests are blocked by robots.txt. The sections stay empty or show skeletons in what Google indexes. AI crawlers never run the JavaScript in the first place. So, to search engines:

- **Stock pages** are a name, one paragraph and six numbers. The parts that make BullPen different (the plain-English company description, the Health Score, the financials) are missing. Google's ~250-word view also looks much like every other stock page, which feeds "Crawled, currently not indexed".
- **`/academy`, `/picks/*` and `/asset/*`** are blank pages with a title.

I couldn't confirm this from inside Google. **To check (2 minutes):** in Search Console, run URL Inspection on `https://bullpeninvest.com/academy` and `/stock/AAPL`, then View crawled page → Screenshot and More info → Page resources. I expect empty sections and `/api/...` rows marked "Blocked by robots.txt".

Don't fix this by removing `Disallow: /api/`. Crawlers would then call the API routes directly, which is the TwelveData cost risk the rule exists for. The fix is to put the content in the HTML.

## 5. Gaps, ranked, with the fix for each

1. **Stock pages: server-render the company description and the Health Score.** Biggest reach: about 518 indexable pages, the most-crawled on the site. The pattern already exists twice. `StockGlance` renders a server summary, and the compare pages read the cache only (`fetchCompareCompany(..., { cacheOnly: true })`), so a crawl never spends credits. Extend the server part of `app/stock/[ticker]/page.tsx`:
   - "What Apple does": the profile description, which the nightly prefetch keeps warm for `SIGNIFICANT_TICKERS`.
   - The Health Score line: score, grade and the strongest and weakest pillar. The compare pages already render exactly this.
   - Optionally, last year's revenue and profit from cached statements.

   Read all of it cache-only; if the cache misses, leave the section out. Two ways to build it: prefetch these queries into the existing `HydrationBoundary` and drop `ssr: false` for `CompanyProfileCard` and `HealthScoreCard`, or add text-only server sections next to `StockGlance`. The second is less code and leaves the interactive cards alone.
2. **`/academy`: render the course catalog on the server.** It is one URL, but it is the entry to the whole Academy and the page Google sees is empty. In `app/academy/page.tsx`, call whatever `/api/academy/courses` calls (signed-out view, zero progress) and either prefetch into a `HydrationBoundary` with the same query key as `useAcademyCourses`, or pass the list as initial data. A small change.
3. **`/picks/[date]`: prefetch the pick on the server.** 18 sitemap URLs, each blank. `generateMetadata` already calls `getPickRowByDate(date)`. Do the same in the page and dehydrate it under `['pick-detail', date]`, so the thesis, entry price and result are in the HTML. A small change.
4. **`/asset/*` (6 commodities): add a server summary or leave the sitemap.** Either a `StockGlance`-style paragraph (price, 52-week range, what moves gold) from the cached snapshot, or drop these six from `app/sitemap.ts` until they have one. Low reach.
5. **Economy hub: prefetch the cached AI summary.** The numbers are already in the HTML, so this is polish. Read the cached summary on the server (the page already has ISR 900 s) so "The short version" is real text instead of "Writing the short version". This is the one paragraph an AI answer engine would quote.
6. **Raw i18n keys in server HTML** (`triggerButtonLabel`, `searchPlaceholder`). Load those namespaces on the server render or give the strings a server-safe default. Small change, also a visible flash for users.
7. **Academy course pages have no canonical.** They are gated and not in the sitemap. Add `robots: { index: false, follow: true }` (or a canonical) to their layout so Google doesn't file them as empty duplicates. Lowest priority.
